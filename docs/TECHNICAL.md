# Technical notes

How TR8orS Kit Loader reads and writes TR-8S data. Everything here was worked out by studying files the TR-8S
exports, from publicly shared community research, and by testing against a real TR-8S. Roland has not published this
format or protocol, so treat it as observed behavior, not a specification. No Roland code or data is included in this
project.

## The `.t8k` kit file (`t8k.py`)

All numbers are little-endian unless noted.

### Header (0x40 bytes)

| Offset | Size | Content |
|---|---|---|
| 0x00 | 4 | `T8K ` |
| 0x04 | 4 | number of chunks |
| 0x08 | 16 | spaces |
| 0x18 | 12 | device id of the exporting unit (the app writes zeros) |
| 0x24 | 12 | zeros |
| 0x30 | 4 | CRC-32 of all chunk headers |
| 0x3C | 4 | CRC-32 of header bytes 0x00–0x3B |

### Chunks

Each chunk has a header with a 4-character tag, its size, the CRC-32 of its body and the CRC-32 of the first 28 header
bytes.

| Tag | Size | Content |
|---|---|---|
| `NAME` | — | kit name |
| `KIT ` | 1312 | kit parameters. Pad tone ids start at 0x184, with a stride of 0x34 per pad. The 11 pad colors are at 0x2A (12 colors). |
| `TONE` | 36 | one per user sample: name, category |
| `PCMT` | 64 | one per user sample: address, size, channels, source id |
| `WAVE` | — | the sample audio (`SMPL` records) |

- Audio is 16-bit, stored **planar** (all left samples, then all right), and padded to whole 128 KB blocks.
- Tone ids 0–521 are the built-in ROM tones. User samples are 624–1023 (the TR-8S shows them as US 1–400).
- In factory kits, a byte of 0xFF in a pad means "default". Byte 4 of each pad struct is derived by the TR-8S itself
  and is ignored when comparing kits.
- The kit parameters (effects, tune, decay…) are not generated by the app. They come from the kit being edited, from
  the destination slot (USB), or from a kit copied once from the user's own TR-8S. The app ships no kit data.

## Memory model (`library.py`)

- User sample memory is 0x03300000 bytes = **408 blocks** of 128 KB, plus **400** sample slots.
- One block is 65,536 16-bit sample frames: 1.49 s of mono at 44.1 kHz. A stereo sample uses two blocks per 1.49 s.
- Every sample is rounded **up** to whole blocks.
- "22.05 kHz" stores the sample at 22,050 Hz, which halves its size. The sample record carries the rate, so the
  TR-8S plays it at the right pitch.

## USB protocol (`tr8s_usb.py`)

The TR-8S appears as a USB MIDI device. The app talks Roland SysEx on the `TR-8S CTRL` port, falling back to the main
`TR-8S` port.

### Message format

```
F0 41 <dev> 00 00 00 45 <cmd> <addr ×4> <data…> <checksum> F7
```

- `dev` is the Device ID minus 1 (0x10 = Device ID 17, the factory setting).
- `cmd` is 0x11 (RQ1, request) or 0x12 (DT1, data).
- The checksum is Roland's standard one, computed over the address and data bytes.
- Binary data is 7-bit packed (7 bytes → 8).
- Windows delivers long SysEx in 1024-byte pieces. The receiver joins them back together before parsing.

### Utility commands (base address 0x50000000)

| Command | Id |
|---|---|
| playing | 0x10 |
| lock panel | 0x11 |
| display text | 0x12 |
| firmware version | 0x13 |
| unit id | 0x14 |
| optimize memory | 0x20 |
| free area | 0x21 |
| free tone count | 0x22 |
| free tone | 0x23 |
| delete tone | 0x24 |
| send kit / tone / PCM tone / sample | 0x50 / 0x60 / 0x70 / 0x72 |
| get kit / tone / PCM tone / sample | 0x51 / 0x61 / 0x71 / 0x73 |

- Bulk data travels in chunks, and the TR-8S reports progress in percent.
- After sending, a kit or tone is committed with the write commands (kit 0x02, tone 0x03).

### Temporary parameters

| Address | Content |
|---|---|
| 0x10000000 | kit name |
| 0x10001000 | the 11 pad tone ids |
| 0x300000xx | tone name / category / type |
| 0x400000xx | sample address / size / channels |

### What the app does over USB

- **Read TR-8S:** reads the firmware version, free memory, every kit (name, pad tone ids) and every user sample (name,
  size, address).
- **Send:**
  1. compares each pad's processed audio with the samples already on the TR-8S, so identical audio is re-used;
  2. uploads only the new samples;
  3. writes the kit;
  4. reads it back to verify.
- **Delete:** first re-points the pads of every kit that uses the samples to the built-in 909 tone for that pad (so
  no kit refers to a deleted sample), then deletes the samples.
- **Optimize:** runs the TR-8S's own defragmentation and follows its progress.
- While working, the app locks the TR-8S panel and shows a short message on its display.

## Audio processing (`app.py`, `Slot.process` and `Slot.render`)

The same chain runs for the `.t8k`, the USB upload and the optional WAV copies:

1. **start/end trim** → **mono** → **HPF/LPF** (4th-order Butterworth) → **normalize** → **volume**;
2. **Fit:** cut to one block with a 30 ms fade;
3. **fades** (S-curve);
4. a 3 ms **de-click** fade at any cut that does not start or end on silence;
5. **22.05 kHz** resample, then conversion to 16-bit.

The sample editor draws the output of `Slot.process` (steps 1–4), so the waveform on screen is exactly what is sent.

A pad with no edits is passed through bit-exact, so the same file always produces the same audio, and it can be
recognized on the TR-8S.

## Self-test (`selftest.py`)

`python selftest.py some-exported-kit.t8k` checks, without hardware:

- `.t8k` round-trips;
- the block maths, Fit and de-click;
- the fades;
- library scanning and type detection;
- memory accounting and limits;
- that SD export leaves the source files untouched;
- project save/load;
- upload tracking and the "already on the TR-8S" warnings;
- the keyboard shortcuts;
- that empty pads fall back to ROM tones;
- that invalid kits (no kit parameters, no samples) are refused.
